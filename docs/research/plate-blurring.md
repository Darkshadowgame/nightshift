# On-device number plate blurring and metadata stripping (iOS, Expo SDK 58)

Research note, 17 November 2026. Covers Nightshift's Phase 2 item: "automatic blurring" (see `docs/SPEC.md`, *Privacy and safety in Phase 1*).

App context checked in this repo: `expo ~58.0.25`, `react-native 0.88.1`, `expo-image-picker ~58.0.10`. The Expo pods declare a minimum of **iOS 16.4** (`ExpoImagePicker.podspec`). The native folders are generated by `expo prebuild` (CNG), and there's no Mac locally, so all native code must live in a config plugin or a local Expo module that CI compiles.

---

## TL;DR recommendation

Build one small **local Expo module in Swift** (`modules/plate-redactor`). It does three things:

1. **Detect** plates with Apple Vision (`VNRecognizeTextRequest`), using a UK plate regex. It merges two-line motorbike plates and also runs on overlapping tiles so small, distant plates are found.
2. **Redact** the regions with Core Image. Use heavy pixelation plus a flat fill, not a light Gaussian blur.
3. **Re-encode** the photo with ImageIO (`CGImageDestination`) and write no metadata, so EXIF, GPS, TIFF and maker notes are all gone.

The JS side shows the detected boxes in a **review screen**. Redaction is on by default, and the user can add, move, resize or remove boxes. Only the redacted, re-encoded file is ever uploaded.

Don't add an ML object detector in v1. Add one in v2 only if real-world recall is too low. If you do, use an Apache-2.0 architecture (YOLOX-Tiny/Nano, D-FINE-N or RF-DETR-Nano), train it yourself on CC-BY plate data, convert it with `coremltools 9.0`, and run it in the same module.

Rough effort: **5–8 developer-days** for v1 (module, review UI and a test set), plus **4–7 days** for an optional v2 detector.

Expected accuracy for v1:
- Clear daytime photos of a whole car or bike, with the plate within about 30° of square-on: **roughly 85–95% recall**.
- Night, glare, steep angles, dirty or partly hidden plates, or plates under about 1.5% of image height: **noticeably worse, perhaps 50–70%**.

These figures are my estimate, not a benchmark. Run the test-set step below to get real numbers. Because of this gap, the manual editor and the "No plate found, check the photo" prompt are part of the design, not optional extras.

## 1. Apple Vision (text and rectangles)

### APIs
- **`VNRecognizeTextRequest`** (iOS 13+). It returns `VNRecognizedTextObservation`s, each with a bounding quad (`topLeft`, `topRight`, `bottomLeft`, `bottomRight`, normalised with the origin at bottom-left) and its top-N candidate strings. Useful settings:
  - `recognitionLevel = .accurate`
  - `usesLanguageCorrection = false` (stops the recogniser "fixing" `AB12 CDE` into words)
  - `minimumTextHeight`: the default ignores small text. Lower it to about 0.01–0.02, or run on tiles.
  - `recognitionLanguages = ["en-GB"]`
  - `customWords` doesn't help with plates.
- **`VNDetectRectanglesRequest`**. Finds quadrilaterals, with settings for aspect ratio (`minimumAspectRatio`/`maximumAspectRatio`), `quadratureTolerance` and `minimumSize`. On its own it is a poor plate detector, because cars are full of rectangles (windows, grilles, lights). It is useful as a **second signal**: an OCR hit inside a rectangle with plate proportions (about 4.7:1 for a standard UK car plate at 520×111 mm, and roughly 1.5:1 or less for motorcycle and square plates) gets a higher score, and its edges give a tighter quad for the mask.
- **New Swift-only Vision API** (`RecognizeTextRequest`, `DetectRectanglesRequest`, async/await, no `VN` prefix). This needs **iOS 18+**. The app's floor is 16.4, so either wrap it in `if #available(iOS 18, *)` or simply use the `VN*` classes, which are not deprecated and cover every supported device. Recommendation: use `VN*` now and switch when the minimum reaches 18. The results are the same, since both APIs use the same models.

### UK plate heuristics
Normalise each candidate string first: uppercase it, remove spaces, dots and dashes, then try confusable swaps by position (`0↔O`, `1↔I`, `5↔S`, `8↔B`, `2↔Z`, `6↔G`). Then match these patterns:

| Format | Era | Regex (after normalising) |
|---|---|---|
| Current | Sept 2001– | `^[A-Z]{2}[0-9]{2}[A-Z]{3}$` (e.g. AB12CDE) |
| Prefix | 1983–2001 | `^[A-Z][0-9]{1,3}[A-Z]{3}$` (e.g. A123BCD) |
| Suffix | 1963–1983 | `^[A-Z]{3}[0-9]{1,3}[A-Z]$` (e.g. ABC123D) |
| Dateless / cherished | pre-1963 and transfers | `^[A-Z]{1,3}[0-9]{1,4}$` or `^[0-9]{1,4}[A-Z]{1,3}$` |
| Northern Ireland | | `^[A-Z]{1,3}[0-9]{1,4}$` (e.g. ABZ1234, overlaps dateless) |

Cherished plates are often spaced to spell words (e.g. "B16 BOY"). Normalising away spaces handles these. Don't try to "validate" the plate. **Any** match should trigger redaction, and so should a near miss. The cost of an extra blur is low.

Signals that raise a weak match's score (use them only to *add* boxes, never to remove one):
- the region is a light, high-contrast area with dark text,
- the background colour is yellow (rear) or white (front),
- there is a blue GB/UK identifier strip on the left,
- the observation's box sits roughly level, low on the vehicle.

**Two-line plates** (motorbikes, some square imported-car plates): Vision returns two separate observations, such as `AB12` above `CDE`. Pair observations whose x-ranges overlap and that are stacked vertically within about 1.5× line height. Concatenate their text, test it against the regex, and redact the **union** quad. UK motorbikes registered since September 2001 must not carry a front plate, so a bike photo normally has only the rear two-line plate.

### Accuracy pitfalls
- **Small plates.** A whole car in a 12 MP photo often puts the plate at 1–3% of image height, near Vision's practical limit. Fix: run the request on the full image **and** on a 2×2 or 3×3 grid of overlapping tiles (25% overlap), then map the boxes back. This takes about 0.3–1 s per photo on an A15+ device at `.accurate` (my estimate). That's fine for upload, but not for live video.
- **Angles.** OCR degrades beyond about 30–45° of yaw. The quad is still returned, so the mask can follow the plate's perspective.
- **Night, flash glare, retro-reflective plates.** Glare often bleaches the characters. Vision may detect text but misread it, so the regex fails. Mitigation: also accept "short alphanumeric text of 5–8 characters, mostly capitals and digits, inside a plate-proportioned rectangle" as a positive.
- **Stylised or illegal fonts and spacing, 3D/4D raised characters, green zero-emission flash, dealer surrounds, dirt, partial occlusion** (tow bar, bike rack, number-plate light).
- **False positives.** Text such as stickers, dealer names or tyre sidewalks can trigger a match. These are cheap to accept, and the user can remove them.
- **Text detection ≠ plate detection.** Vision has no idea what a plate is. Anything it can't read, it can't find. This is the main reason to consider a v2 object detector.

## 2. Core ML licence-plate object detectors

A dedicated detector finds the *plate object* even when the characters are unreadable (night, angle, blur). That is the main recall gain over OCR.

| Option | Licence | Notes |
|---|---|---|
| Ultralytics YOLOv8/YOLO11/YOLO26 (`ultralytics` 8.4.215 on PyPI) and most "yolov8-license-plate" / "yolov11-license-plate" weights on HF/GitHub (e.g. `morsetechlab/yolov11-license-plate-detection`) | **AGPL-3.0** (Ultralytics' position is that trained weights and exported models are covered too). Commercial "Enterprise" licence costs money. | **Avoid** for a closed-source app unless you buy the licence. Many HF model cards omit the licence, so treat these as AGPL. |
| `open-image-models` (PyPI 0.6.0, used by `fast-alpr` 0.4.0): YOLOv9-t/s plate detectors at 256–640 px, ONNX, mAP50-95 0.61–0.77 | Repo badge is **MIT**, but the README doesn't state the weights' licence, training code or dataset. The original YOLOv9 repo (WongKinYiu) is **GPL-3.0**. | Fine for quick **prototyping and benchmarking**. Don't ship without written confirmation of the weights' provenance and licence. |
| **YOLOX** (Megvii, `yolox` 0.3.0) | **Apache-2.0** | YOLOX-Nano (~0.9M params, ~2 MB) or YOLOX-Tiny (~5M params, ~10 MB FP16). Simple conv graph that traces cleanly to Core ML. **Train it yourself**, since no reliable pre-trained plate weights with a clear licence exist. |
| **RF-DETR** (Roboflow, `rfdetr` 1.12.1) | **Apache-2.0** for Nano/Small/Medium (check the larger variants, which have used a different licence) | Strong accuracy at small sizes. DETR-style ops convert to Core ML less smoothly than YOLOX, so budget extra time. |
| **D-FINE / RT-DETR / RT-DETRv2** | **Apache-2.0** | Apache-licensed plate fine-tunes exist on HF (e.g. `justjuu/rtdetr-v2-license-plate-detection`, `Garon16/rtdetr_r50vd_russia_plate_detector_lightning`), but they are R50 backbones (~170 MB), too big for an app download. Use the N/S sizes and retrain. |
| `nickmuchi/yolos-small-rego-plates-detection`, `detr-resnet50-license-plate-detection` | Apache-2.0 | Transformer, about 100+ MB, slow on device. Useful only as a reference. |
| MobileNet-SSD / EfficientDet-Lite (TF/TFLite) | Apache-2.0 | Older but small. Fine if you prefer the TFLite toolchain, though Core ML is the native path on iOS. |
| **OpenALPR** | **AGPL-3.0** or a paid commercial licence (Rekor). Repo last updated in early 2024. | Not suitable: AGPL, a C++ build burden, and its focus is reading plates, not redacting them. |

**Training data:** use plate datasets licensed **CC BY 4.0** (many Roboflow Universe "license plate" sets are; check each one), plus your own UK photos. Include yellow rear, white front and two-line bike plates, and night images. 2–5k labelled images is enough for a one-class detector. Keep the attribution file in the repo.

**Conversion:** PyTorch → `torch.jit.trace`/`torch.export` → `coremltools` 9.0 (`ct.convert(..., convert_to="mlprogram", compute_precision=FLOAT16)`). Output an `.mlpackage` and add NMS on the Swift side, or build a pipeline with an NMS model. Run it via `VNCoreMLRequest` so Vision handles scaling and orientation. Conversion runs on Linux. Compiling `.mlpackage` → `.mlmodelc` happens in the Xcode build in CI (or use `xcrun coremlcompiler` there). Expected size is about 2–12 MB, and inference about 5–20 ms per 640 px pass on the Neural Engine. Again, run it on tiles for small plates.

Combine its output with the Vision OCR hits by union (with IoU merge). The detector supplies recall, and OCR confirms the hit and tightens the box.

### How to redact a region (Core Image)
1. Load with `CGImageSourceCreateWithURL` and create a thumbnail at full size with `kCGImageSourceCreateThumbnailWithTransform = true`. This bakes in the orientation, so there is no orientation tag left to keep.
2. Build a **mask**: a black `CGContext` with each plate quad filled in white, padded by about 15%. Feathering is optional.
3. Pixelate: `CIFilter.pixellate()` with `scale = max(16, plateHeight/3)` px. Optionally add a flat mean-colour fill or noise over it as well.
4. `CIFilter.blendWithMask()` (input = pixelated, background = original, mask = step 2), then render with a single shared `CIContext`.
5. Encode with `CGImageDestinationCreateWithURL(... kUTTypeJPEG / public.jpeg ...)` and `kCGImageDestinationLossyCompressionQuality = 0.85`. **Pass no metadata dictionary.** Optionally pass `kCGImageDestinationImageMaxPixelSize = 2048–3000` to shrink uploads.

**Use heavy pixelation or a solid fill, not a soft Gaussian blur.** UK plates use one fixed typeface (Charles Wright 2001) and a small set of characters. Lightly blurred or finely mosaicked plates of known fonts have been reversed by template matching and ML deblurring. Big blocks (3 or fewer cells per character height) or an opaque box remove the information. `CIGaussianBlur` with a radius at least as big as the plate height is acceptable if you prefer the look, but pixelate plus fill is the safe default.

## 4. UX fallback (always on by default)

- **Pipeline:** pick photo → module runs `detect` (spinner, under about 1 s) → **Review screen** shows the photo with red boxes over each detected plate → user can **tap to remove**, **drag or resize**, or **"+ Add blur"** (drop a box, then pinch) → **Upload** runs `redact` and uploads only the output file.
- When nothing is detected, show: "We didn't find a number plate. Check the photo before posting," and default the add-box tool to open. Don't allow a silent upload.
- The setting "Blur plates automatically" is **on** by default. Turning it off gives a warning (it's the user's own plate, but other cars appear in meet photos too). The detected *text* is **never** sent to JS, stored or logged. Only the boxes are.
- Implementation: `react-native-gesture-handler` 3.5.0 + `react-native-reanimated` 4.7.1 (or `react-native-svg`, already installed at 15.16.0, for the box overlay). Work with boxes as normalised 0–1 coordinates relative to the oriented image, so screen scaling doesn't matter.
- Pre-blur on the preview too, by drawing pixelated boxes in the editor, so what users see is what gets uploaded.

## 5. Server-side alternatives (for completeness)

- **Plate Recognizer** (Snapshot API and the "Blur" product, paid, cloud or on-prem Docker), **AWS Rekognition** `DetectText`/Custom Labels, **Google Cloud Vision** text and object detection, **Azure AI Vision** OCR. Self-hosted: run YOLOX/RF-DETR or `fast-alpr` in a worker on upload.
- **Pros:** bigger models give better recall at night and at angles, you can update models without app releases, and one pipeline serves iOS, Android and web.
- **Why on-device is preferable here:**
  - The *unredacted original* (plate and usually GPS) would leave the phone and land on your servers and possibly a third-party processor. Number plates can identify a person, so they are typically personal data under UK GDPR, and so is location. That brings DPA, retention and breach obligations.
  - Each processor is another party to vet, and per-image costs scale with use.
  - Users can see the result before it's sent.
  - It works offline or on poor signal at meets.
- **Pragmatic hybrid (optional, later):** keep on-device redaction as the gate. A server-side detector can then run on the **already-redacted** image as a second check that flags residual plates for moderation. It never sees an unredacted original.

## 6. EXIF and GPS stripping

What the code in this repo and the current packages actually do:

- **`expo-image-picker` 58.0.10, iOS library path (PHPicker):** with `quality` at the default `1.0`, a JPEG is returned **as the original bytes** (`return (rawData, ".jpg")`), and HEIC/TIFF/AVIF are also passed through raw (`ImageUtils.swift`). That means **EXIF including GPS is kept in the file** even though `exif: false` only controls what's returned to JS. With `quality < 1`, JPEGs are re-encoded via `UIImage.jpegData`, which writes no EXIF or GPS, but HEIC is still passed through raw. **Don't rely on the picker to strip metadata.**
- **Camera path:** re-encoded via `UIImage.jpegData`. The docs note there are no GPS tags in the camera case. Still, run it through the same redaction step.
- **`expo-image-manipulator` 58.0.16:** `renderAsync()` → `saveAsync({ format: JPEG, compress })` re-encodes via `UIImage.jpegData` / `pngData` on iOS and `Bitmap.compress` on Android. Both write pixels only, so **EXIF and GPS are dropped** (orientation is baked into the pixels at load). The docs don't promise this, and an old forum thread confirms metadata loss as a side effect. Treat it as implementation behaviour: verify it with a test and keep a server-side check.
- **Recommended:** the native module's `redact` step writes through `CGImageDestination` with **no properties** for *every* upload, even when no plate was found. That gives one guaranteed metadata-free path. Add a CI or unit test (`CGImageSourceCopyPropertiesAtIndex` on the output) that asserts there is no `{GPS}`, `{Exif}`, `{TIFF}` or `{MakerApple}` dictionary.
- **Belt and braces:** the server rejects or strips any upload that still has EXIF (e.g. with `exiftool -all=` or `sharp().rotate()` without `withMetadata()`), and logs it, which shows the client step failed.
- iOS also lets users turn off location in the share sheet and some picker flows, but that is user-controlled. Don't depend on it.

## Implementation sketch (recommended approach)

### Module API (TypeScript)
```ts
// modules/plate-redactor/index.ts
export type Quad = { tl: Pt; tr: Pt; br: Pt; bl: Pt }; // normalised 0..1, origin top-left, oriented image
export type Pt = { x: number; y: number };
export type PlateBox = {
  id: string;
  quad: Quad;
  score: number;                 // 0..1
  source: 'ocr' | 'ocr-2line' | 'rect' | 'model' | 'user';
};

export function detectPlates(
  uri: string,
  opts?: { tiles?: 1 | 4 | 9; minTextHeight?: number }   // default tiles: 4
): Promise<{ width: number; height: number; boxes: PlateBox[] }>;

export function redact(
  uri: string,
  boxes: Pick<PlateBox, 'quad'>[],
  opts?: { style?: 'pixelate' | 'fill'; maxPixelSize?: number; quality?: number }
): Promise<{ uri: string; width: number; height: number }>;   // new file in cache, no metadata
```
Implement both as `AsyncFunction` in `PlateRedactorModule.swift`. Do the work on a background queue, and never return the recognised text.

### Steps
1. `npx create-expo-module@latest --local plate-redactor`. Set `platforms: ["apple"]` in `expo-module.config.json`. Stub Android or web to return `[]` and fall back to `expo-image-manipulator` re-encoding for stripping. **(0.5 day)**
2. Swift `detectPlates`: load the oriented CGImage, build tiles, run `VNRecognizeTextRequest` (accurate, no language correction, top-3 candidates) and `VNDetectRectanglesRequest` per tile, map boxes back, merge two-line pairs, normalise and match the regex, score, then NMS. **(2 days)**
3. Swift `redact`: mask, then `CIPixellate`/fill, then blend, then `CGImageDestination` with no metadata. **(1 day)**
4. Review screen (`src/app/...`) with an SVG overlay and gesture handles, plus add and remove actions. Wire it into the Garage photo flow (`expo-image-picker` → `detectPlates` → review → `redact` → upload). **(2–3 days)**
5. Test set: about 150–300 real photos (cars front and rear, bikes, day and night, angles, meets with several cars). Store the boxes as JSON and write a small eval script that records recall and false positives per category. Also add a metadata-free assertion test. Run it in CI on the simulator via xcodebuild test, or with a Detox/Maestro smoke test. **(1–2 days)**
6. CI: no config plugin needed, since `expo prebuild` autolinks `modules/`. Make sure the CI xcodebuild uses `-workspace ios/*.xcworkspace` after `pod install`, as now.

### v2 (only if the eval shows recall too low)
Train YOLOX-Tiny (or RF-DETR-Nano) on CC-BY plus your own UK images. Export with `coremltools` 9.0 to FP16 `.mlpackage` and bundle it in `modules/plate-redactor/ios/` (podspec `resources`). Run it with `VNCoreMLRequest` on the same tiles and union its boxes with the OCR boxes. Before training, benchmark the `open-image-models` ONNX on your test set to see the likely gain. Rough effort is 4–7 days, mostly data labelling.

### Expected limits (be explicit to users)
- v1 (OCR-based) misses plates it cannot *read*: night glare, steep angles, motion blur, dirt, tiny distant cars in meet shots. It may also miss oddly spaced cherished plates whose characters Vision misreads.
- False positives on stickers, dealer badges and signage are expected and harmless.
- Nothing here is perfect, so the review step and the default-on prompt are the safety net. Wording should say "We try to blur plates. Please check before posting," never "plates are guaranteed hidden."
